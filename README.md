# ফিল্ডব্রিজ

বাংলাদেশের কৃষক ও ক্রেতার মধ্যে কৃষিপণ্য কেনাবেচা এবং সরবরাহ সমন্বয়ের উদ্যোগ। কৃষকের OTP-সহ নিবন্ধন, ক্রেতার আবেদন ও অ্যাডমিনের সিদ্ধান্ত, লগইন, ফসলের বিজ্ঞাপন, বাজারে খোঁজ, চাহিদার সঙ্গে সরবরাহের মিল, অর্ডার ও মজুত সংরক্ষণ, কৃষকের আলাদা গ্রহণ/প্রত্যাখ্যান এবং অ্যাপের নোটিফিকেশন চালু আছে।

## প্রযুক্তি

ফ্রন্টএন্ডে React, Vite ও Tailwind CSS। ব্যাকএন্ডে Node.js ও Express। ডেটাবেসের জন্য MySQL এবং Sequelize-এর সংযোগ কনফিগারেশন প্রস্তুত। Node.js 22.12 বা তার পরের সংস্করণ ব্যবহার করুন।

nvm ব্যবহার করলে মূল ফোল্ডারে `nvm use` দিয়ে `.nvmrc` অনুযায়ী Node.js নির্বাচন করতে পারেন।

## চালু করার নিয়ম

দুটি আলাদা টার্মিনাল ব্যবহার করুন।

প্রথম টার্মিনালে প্রকল্পের মূল ফোল্ডার থেকে:

```bash
npm install
cp -n .env.example .env
npm run db:migrate
npm run dev
```

সার্ভারের ঠিকানা: `http://127.0.0.1:5001`।

দ্বিতীয় টার্মিনালে:

```bash
cd client
npm install
cp -n .env.example .env
npm run dev
```

ফন্ট, রঙ ও সম্পূর্ণ About পেজ দেখতে সরাসরি **http://localhost:5174/about** খুলুন।

নিজের `.env` আগে থেকেই থাকলে `cp` চালাবেন না। `.env` ছাড়াও প্রাথমিক নকশা এবং সার্ভারের সাধারণ স্বাস্থ্য পরীক্ষা চালানো যাবে; নিবন্ধন ও লগইনের জন্য MySQL সংযোগ এবং মাইগ্রেশন প্রয়োজন।

## এক কমান্ডে ডেমো ডেটা

মূল `.env`-এ ডেভেলপমেন্ট MySQL ডেটাবেসের সংযোগ দেওয়া থাকলে প্রকল্পের মূল ফোল্ডারে চালান।

```bash
npm run demo
```

কমান্ডটি প্রয়োজনীয় মাইগ্রেশন চালিয়ে ৫ জন কৃষক, ৪ জন ক্রেতা, ১ জন অ্যাডমিন, ছবিসহ ২০টি বিজ্ঞাপন, ১৩টি ক্রয় চাহিদা ও ৫টি অর্ডার তৈরি করে। একই ডেটাবেসে আবার চালালে ডেমোর সংখ্যা বাড়ে না এবং অ্যাপে করা পরিবর্তনও থাকে। সাতটি ফসলের ছবি প্রকল্পেই রাখা আছে, তাই ডেমো চালাতে ছবি ডাউনলোডের প্রয়োজন হয় না। [ছবির উৎস ও লাইসেন্স](scripts/demo/crops/CREDITS.md)

ডেমোর ক্রেতার **আলু** চাহিদায় সব জাতের আলু বিবেচনা করা হয়। **লাল আলু** চাহিদায় শুধু কৃষক ৩-এর লাল আলুর বিজ্ঞাপনটি মিলবে। বাজারে `potato`, `alu` বা `আলু` দিয়ে আলু খুঁজুন। মিষ্টি আলু আলাদা ফসল।

লগইনের জন্য নিচের নামের শেষে `@fieldbridge.example` যোগ করুন। সব ডেমো অ্যাকাউন্টের পাসওয়ার্ড প্রথমবার তৈরি হয়ে স্থানীয় `uploads/demo-login.txt` ফাইলে থাকে।

| লগইন নাম | কোথায় কী দেখবেন |
| --- | --- |
| `buyer` | `/requirements`-এ নিচের ছয়টি মিল, `/orders`-এ অপেক্ষমাণ অর্ডার, আংশিক গ্রহণ ও বিকল্প কৃষক |
| `wholesale` | পূরণ হওয়া ও বন্ধ চাহিদা, গৃহীত ও প্রত্যাখ্যাত অর্ডার, পড়া ও অপঠিত নোটিফিকেশন |
| `farmer1` থেকে `farmer5` | `/account/listings`-এ নিজস্ব ফসল। `farmer1` মূল অর্ডার ও `farmer4` বিকল্প সরবরাহের অনুরোধে উত্তর দিতে পারেন |
| `pending`, `rejected` | `/account`-এ আবেদনের অবস্থা, জমা দেওয়া নমুনা নথি ও প্রযোজ্য ক্ষেত্রে প্রত্যাখ্যানের কারণ |
| `admin` | `/admin/buyers`-এ আবেদন ও নথি দেখা এবং অপেক্ষমাণ আবেদনের সিদ্ধান্ত দেওয়া |

| ফসল ও চাহিদা | ডেমো মজুত দিয়ে মিল |
| --- | --- |
| আলু, ১০০ কেজি | এক কৃষকের ঠিক ১০০ কেজি। আরেকজনের ১১২ কেজি থেকে একক অর্ডারে ১০০ নিলে ১২ কেজি থাকে |
| টমেটো, ১০০ কেজি | দুই কৃষকের ৬০ + ৪০ কেজিতে পুরো চাহিদা। ৬০ + ৪৫ নিলে ৫ কেজি বাড়তি |
| গাজর, ১০০ কেজি | তিনজনের ২০ + ৩০ + ৫০ কেজিতে পুরো চাহিদা |
| মিষ্টিকুমড়া, ৫০টি | ২২ + ৩৮ = ৬০টি ঠিক ২০% বাড়তির সীমায়। ২২ + ৩৯ = ৬১টি সীমা ছাড়ায়, তাই ওই জুটি দেখাবে না |
| শসা, ১ টন | দুইজনের ০.৩৫ + ০.৪৫ = ০.৮০ টন। এখনও ০.২০ টন প্রয়োজন |
| মূলা, ৭০ কেজি | ডেমোর একটি বিজ্ঞাপন বন্ধ, অন্যটির বিক্রি শেষ। সরবরাহের মিল নেই |

একই ডেটাবেসে অন্য কৃষকের চালু বিজ্ঞাপন থাকলে সেগুলোও স্বাভাবিক নিয়মে মিলে আসতে পারে। ভুট্টার অর্ডারগুলো দিয়ে মজুত সংরক্ষণ, প্রত্যাখ্যান ও বিকল্প কৃষকের কাজ দেখা যায়।

## এখন যে পাতাগুলো রয়েছে

| ঠিকানা | বর্তমান অবস্থা |
| --- | --- |
| `/about` | উদ্দেশ্য, লক্ষ্য ব্যবহারকারী ও পরিকল্পনাসহ পরিচিতি পাতা |
| `/` | প্রথম পাতার জন্য নির্মাণাধীন 404 |
| `/marketplace` | ফসলের বাজার; নাম, অবস্থান, একক, পরিমাণ, তারিখ ও অনুমোদিত ক্রেতার জন্য দাম দিয়ে ফিল্টার |
| `/marketplace/:id` | ছবি, মজুত, তারিখ ও অনুমোদন অনুযায়ী দাম এবং কৃষকের যোগাযোগের তথ্য |
| `/requirements` | অনুমোদিত ক্রেতার নিজের ক্রয় চাহিদা; অবস্থা ও বাকি সম্পাদনার সংখ্যা |
| `/requirements/new` | নতুন ক্রয় চাহিদা তৈরি |
| `/requirements/:id/edit` | নিজের চাহিদা সম্পাদনা; সর্বোচ্চ দুইবার |
| `/requirements/:id/matches` | চাহিদার সম্মিলিত সরবরাহের পাতায় নিয়ে যায় |
| `/requirements/:id/combinations` | নিজের চাহিদার জন্য সর্বোচ্চ পাঁচটি সম্মিলিত সরবরাহের সমন্বয় |
| `/orders` | ক্রেতার নিজের অর্ডার; কৃষকের জন্য শুধু তাঁর অংশ আছে এমন অর্ডার |
| `/orders/:id` | সংরক্ষিত অর্ডারের তথ্য, পরিমাণের হিসাব ও কৃষকের নিজের উত্তর |
| `/notifications` | আগের খবর, পড়া বাকি সংখ্যা, অর্ডার খোলা ও পড়া চিহ্নিত করা |
| `/login` | ফোন নম্বর বা যুক্ত করা ইমেইল দিয়ে কৃষক, ক্রেতা ও অ্যাডমিনের লগইন |
| `/register` | কৃষকের নিবন্ধন এবং ফোন OTP যাচাই |
| `/register/buyer` | ক্রেতার নিবন্ধনের আবেদন |
| `/account` | নিজের নিবন্ধিত তথ্য; লগইন ছাড়া প্রবেশ করা যাবে না |
| `/account/listings` | কৃষকের নিজের বিজ্ঞাপন, অবস্থাভিত্তিক বাছাই ও পরিচালনা |
| `/account/listings/new` | ছবি ও প্রয়োজনীয় তথ্য দিয়ে নতুন ফসলের বিজ্ঞাপন |
| `/account/listings/:id/edit` | নিজের বিজ্ঞাপনের তথ্য, মজুত ও ছবি সম্পাদনা |
| `/admin/buyers` | শুধু অ্যাডমিনের জন্য ক্রেতার আবেদন পর্যালোচনা |
| অন্য যেকোনো ঠিকানা | সাধারণ বাংলা 404 |

মোবাইলে মেনু খোলা ও বন্ধ করা যায়। Escape চাপলেও মেনু বন্ধ হবে। লগইন করলে নিজের অ্যাকাউন্ট বা অ্যাডমিন প্যানেল এবং লগআউটের নিয়ন্ত্রণ দেখা যাবে। কৃষক ও ক্রেতার জন্য **আমার অর্ডার** ও নোটিফিকেশনের ঘণ্টাও আছে। প্রত্যাখ্যাত সরবরাহের জন্য ক্রেতা বিকল্প কৃষক বেছে নিতে পারেন। কৃষক নিজের অ্যাকাউন্টে **প্রোফাইল সম্পাদনা** থেকে নাম, ইমেইল, ছবি ও খামারের তথ্য সংরক্ষণ করতে পারেন। গৃহীত অংশের অগ্রগতি অর্ডারের বিস্তারিত পাতায় দেখা যায়।

## অ্যাডমিন তৈরি

মূল `.env.example`-এর `ADMIN_NAME`, `ADMIN_PHONE`, `ADMIN_EMAIL` ও `ADMIN_PASSWORD` মূল `.env`-এ যোগ করে নিজের মান বসান। `ADMIN_PHONE` এবং ১২–১২৮ অক্ষরের `ADMIN_PASSWORD` আবশ্যক; ইমেইল ঐচ্ছিক। নাম না দিলে “ফিল্ডব্রিজ অ্যাডমিন” ব্যবহার হবে। পাসওয়ার্ডে `#` বা ফাঁকা জায়গা থাকলে মানটি উদ্ধৃতির মধ্যে রাখুন।

প্রকল্পের মূল ফোল্ডারে চালান:

```bash
npm run db:migrate
npm run admin
```

তারপর **http://localhost:5174/login** থেকে সেই ফোন বা ইমেইল ও পাসওয়ার্ড দিয়ে প্রবেশ করুন। অ্যাডমিনকে সরাসরি `/admin/buyers`-এ নেওয়া হবে। অ্যাডমিন তৈরির কোনো পাবলিক ওয়েব ফর্ম বা API নেই।

একই পরিচয়ে `npm run admin` আবার চালালে পুরোনো অ্যাডমিনের পাসওয়ার্ড বা তথ্য পরিবর্তিত হবে না। কৃষক বা ক্রেতার ফোন/ইমেইল দিলে তাদের অ্যাকাউন্টকে অ্যাডমিনে রূপান্তর করা হবে না। অ্যাডমিন তৈরির পর শুধু `.env` বদলালে ডেটাবেসের পাসওয়ার্ড বদলায় না।

## ক্রেতার আবেদন ও অনুমোদন

১. **http://localhost:5174/register/buyer** থেকে নাম, ফোন, পাসওয়ার্ড, ব্যবসা/প্রতিষ্ঠানের নাম, ব্যবসার ধরন এবং পূর্ণ ঠিকানা লিখুন। ইমেইল ঐচ্ছিক। নিবন্ধন পাতার ওপরেও কৃষক বা ক্রেতা বেছে নেওয়া যায়।

২. আবেদন জমা হলে ক্রেতা লগইন করতে পারবেন এবং `/account`-এ “অনুমোদনের অপেক্ষায়” অবস্থা দেখবেন। কৃষকের নিবন্ধনের OTP নিয়ম অপরিবর্তিত; ক্রেতার ফোনকে OTP-যাচাইকৃত হিসেবে চিহ্নিত করা হয় না।

৩. অ্যাডমিন আবেদন তালিকা থেকে ক্রেতার নাম, ফোন, ইমেইল, প্রতিষ্ঠান, ব্যবসার ধরন, ঠিকানা এবং নিবন্ধনের তারিখ দেখে সিদ্ধান্ত দেবেন। প্রত্যাখ্যান করলে ৫–৫০০ অক্ষরের কারণ আবশ্যক।

৪. প্রত্যাখ্যাত ক্রেতা নিজের অ্যাকাউন্টে কারণ দেখবেন এবং নাম, ইমেইল ও ব্যবসার তথ্য সংশোধন করে পুনরায় আবেদন করতে পারবেন। ফোন পরিবর্তন করা যাবে না। পুনরায় জমা দিলে আগের সিদ্ধান্ত বাতিল হয়ে আবেদন আবার অপেক্ষমাণ হবে।

৫. অন্য অবস্থায় ক্রেতা শুধু নাম ও ইমেইল সম্পাদনা করতে পারবেন। অ্যাডমিন সিদ্ধান্ত দেওয়ার পর ক্রেতা পেজ রিফ্রেশ বা “অবস্থা হালনাগাদ” দিয়ে নতুন অবস্থা দেখতে পারবেন।

এক অ্যাকাউন্টের ভূমিকা পরিবর্তন করা যায় না। একই ফোন/ইমেইল একাধিক অ্যাকাউন্টে ব্যবহার করা যায় না। ক্রেতার দেওয়া `role` বা `status` দিয়ে অ্যাডমিন হওয়া বা নিজেকে অনুমোদন দেওয়া যায় না। আবেদন বদলে গেলে পুরোনো সংস্করণ দেখে সিদ্ধান্ত দেওয়া রোধ করা হয়। অনুমোদিত ক্রেতা নিজের অ্যাকাউন্টের **আমার ক্রয় চাহিদা** থেকে চাহিদা পরিচালনা ও মিল থেকে অর্ডার দিতে পারবেন।

## কৃষকের ফসলের বিজ্ঞাপন

কৃষক হিসেবে লগইন করে **আমার অ্যাকাউন্ট → আমার বিজ্ঞাপন** খুলুন। **নতুন বিজ্ঞাপন** থেকে ফসলের নাম, মজুতের পরিমাণ, একক, প্রতি এককের প্রত্যাশিত দাম, ফসল কাটার তারিখ, সরবরাহ শুরুর তারিখ, খামারের অবস্থান ও বিবরণ দিন। বাংলা বা ইংরেজি নাম লিখে তালিকা থেকে ফসল ও প্রয়োজনে জাত বেছে নিন। একই ফসলের একাধিক বিজ্ঞাপন দেওয়া যায়। মান বা গ্রেডের ঘর নেই।

একক হিসেবে কেজি, মেট্রিক টন বা পিস বেছে নেওয়া যায়। পরিমাণে সর্বোচ্চ ৩ ঘর এবং দামে ২ ঘর দশমিক গ্রহণ করা হয়; পিস পূর্ণসংখ্যা হতে হবে। বাংলা ও ইংরেজি সংখ্যা গ্রহণ করা হয়। সরবরাহের তারিখ ফসল কাটার তারিখের আগে হতে পারবে না; আগে কাটা ফসলের বিজ্ঞাপনও দেওয়া যায়।

প্রতিটি বিজ্ঞাপনে ১–৫টি JPG, PNG বা WebP ছবি আবশ্যক; প্রতিটি সর্বোচ্চ ১০ মেগাবাইট। প্রকৃত ছবি যাচাই করে সর্বোচ্চ ১২৮০ পিক্সেলের WebP-তে রূপান্তর এবং ছবির metadata বাদ দেওয়া হয়। প্রথম ছবিটি তালিকায় প্রধান ছবি হবে। সম্পাদনায় পুরোনো ছবি সরানো ও নতুন ছবি যোগ করা যায়।

খামারের ঠিকানা প্রোফাইল থেকে আগে বসে, তবে বিজ্ঞাপনের জন্য আলাদা ঠিকানা লেখা যায়; এতে প্রোফাইল বদলায় না। প্রকাশিত বিজ্ঞাপন সম্পাদনা, সাময়িক বন্ধ ও পুনরায় চালু করা যায়। **বিক্রি শেষ** করলে মজুত শূন্য হয়; আবার চালু করতে আগে সম্পাদনা করে নতুন মজুত লিখুন, তারপর **চালু করুন** চাপুন। **মুছুন** নিশ্চিত করলে বিজ্ঞাপন ও ছবিগুলো স্থায়ীভাবে মুছে যায়।

কৃষকের ব্যক্তিগত বিজ্ঞাপন পরিচালনার API শুধু মালিক কৃষকের জন্য। চালু ও শূন্যের বেশি মজুতের বিজ্ঞাপন এবং তার ছবি আলাদা বাজারের API-তে দেখা যায়। একাধিক ট্যাবে একই বিজ্ঞাপন বদলালে পুরোনো সংস্করণ দিয়ে নতুন তথ্য মুছে লেখা যাবে না; সর্বশেষ তথ্য এনে আবার চেষ্টা করতে হবে। অ্যাডমিনের বিজ্ঞাপন সম্পাদনা বা মুছে ফেলার প্যানেল পরবর্তী ধাপ।

আগে থেকে প্রকল্প চালালে মূল ফোল্ডার থেকে একবার `npm run db:migrate` চালিয়ে নতুন `crop_listings` টেবিল প্রস্তুত করুন। আগের অ্যাকাউন্টের তথ্য এতে বদলায় না।

## ফসলের বাজার ও তথ্য দেখার অনুমতি

কৃষক নিবন্ধন, প্রোফাইল, ফসলের বিজ্ঞাপন, বাজার ও বিকল্প সরবরাহের জেলা–উপজেলার তালিকায় বাংলা বা ইংরেজিতে খুঁজুন। যেমন, `Bogura` বা `বগুড়া` বেছে নিলে উপজেলার তালিকায় ওই জেলার `Shibganj` বা `শিবগঞ্জ` পাওয়া যাবে। জেলা বদলালে আগের উপজেলা নির্বাচন মুছে যায়। তালিকাটি অ্যাপের সঙ্গে থাকে। [তথ্যের উৎস](https://github.com/iqbalhasandev/bangladesh-geo-json)

**http://localhost:5174/marketplace** থেকে ফসলের নাম, জেলা ও উপজেলা দিয়ে খুঁজুন। **আরও ফিল্টার**-এ মজুতের পরিমাণ, ফসল কাটার তারিখ এবং সরবরাহ শুরুর তারিখের সীমা দেওয়া যায়। অনুমোদিত ক্রেতা বা অ্যাডমিন প্রতি এককের দামের সীমা এবং দাম অনুযায়ী সাজানোর সুবিধাও পাবেন। দাম বা পরিমাণ তুলনা করার আগে কেজি, মেট্রিক টন অথবা পিস বেছে নিতে হবে; আলাদা এককের পরিমাণ বা দাম একসঙ্গে তুলনা করা হয় না।

ফিল্টারে বাংলা সংখ্যা গ্রহণ করা হয়। খোঁজার লেখা আংশিক মিলিয়ে পাওয়া যায়; `%` ও `_` সাধারণ লেখা হিসেবে গণ্য হয়। প্রতি পাতায় সর্বোচ্চ ১২টি বিজ্ঞাপন থাকে। ফিল্টার, সাজানো ও পাতার নম্বর URL-এ থাকে; বিস্তারিত পাতা থেকে ফিরলে আগের খোঁজ বজায় থাকে। প্রবেশের লিংক দিয়ে লগইন করলেও সেই বিজ্ঞাপনে ফিরে আসা যায়।

| দর্শক | দেখা যাবে | গোপন থাকবে |
| --- | --- | --- |
| লগইন ছাড়া, অপেক্ষমাণ/প্রত্যাখ্যাত ক্রেতা, কৃষক | ছবি, নাম, পরিমাণ, একক, জেলা–উপজেলা ও তারিখ | দাম, বিস্তারিত বিবরণ, কৃষকের নাম/ফোন ও পূর্ণ ঠিকানা |
| অনুমোদিত ক্রেতা ও অ্যাডমিন | উপরোক্ত তথ্য, দাম, বিবরণ এবং বিস্তারিত পাতায় কৃষকের নাম, ফোন, খামারের নাম ও ওই বিজ্ঞাপনের খামারের ঠিকানা | কৃষকের NID, ইমেইল, পাসওয়ার্ড/সেশন এবং অন্যান্য ব্যক্তিগত অ্যাকাউন্টের তথ্য |

দামভিত্তিক ফিল্টার ও সাজানো সীমিত দর্শকদের জন্য API-তেও নিষিদ্ধ; শুধু পর্দায় লুকিয়ে রাখা হয়নি। খামারের ঠিকানা বিজ্ঞাপন থেকে আসে, কারণ সেটি অ্যাকাউন্টের ঠিকানা থেকে আলাদা হতে পারে। প্রতিটি অনুরোধে বর্তমান অনুমোদন যাচাই করা হয়; সিদ্ধান্ত বদলানোর পরে **তথ্য হালনাগাদ করুন** বা তালিকার হালনাগাদ বাটন চাপলে নতুন অবস্থা কার্যকর হবে।

বন্ধ, বিক্রি শেষ, মজুত শূন্য বা মুছে ফেলা বিজ্ঞাপন বাজারের তালিকা, বিস্তারিত ও ছবির ঠিকানা দিয়ে দেখা যাবে না। সক্রিয় বিজ্ঞাপনের ছবিগুলো প্রকাশ্য; ছবি আপলোডের সময় metadata সরানো হয়। বাজারের উত্তরগুলো `Cache-Control: no-store` ব্যবহার করে। ছবি গ্যালারির ছোট ছবি চেপে অন্য ছবি দেখা যায়; ফোন নম্বর চাপলে কল করার অ্যাপ খোলে। অর্ডার দেওয়ার সুবিধা এই ধাপে যোগ করা হয়নি।

## ক্রেতার ক্রয় চাহিদা

অনুমোদিত ক্রেতা হিসেবে **ক্রয় চাহিদা → নতুন চাহিদা** খুলুন। ফসলের নাম, প্রয়োজনীয় পরিমাণ, একক এবং ডেলিভারির পূর্ণ ঠিকানা আবশ্যক; কৃষকের জন্য অতিরিক্ত নির্দেশনা ঐচ্ছিক। ঠিকানা প্রথমে ব্যবসার প্রোফাইল থেকে বসে, তবে এই চাহিদার জন্য বদলানো যায়। পরিমাণে বাংলা সংখ্যা এবং সর্বোচ্চ ৩ ঘর দশমিক গ্রহণ করা হয়; পিস পূর্ণসংখ্যা হবে। বাজেট, প্রত্যাশিত দাম ও ডেলিভারির তারিখের ঘর নেই।

প্রতিটি চাহিদা তৈরির পর সর্বোচ্চ **২ বার** তথ্য সম্পাদনা করা যাবে। তালিকা ও ফর্মে ব্যবহৃত এবং বাকি সুযোগের সংখ্যা দেখায়। তথ্য না বদলে সংরক্ষণ করলে কোনো সুযোগ ব্যবহার হয় না। দ্বিতীয় পরিবর্তনের পরে ফর্ম এবং API উভয় জায়গায় সম্পাদনা বন্ধ হয়। একাধিক ট্যাবের একই সংস্করণ দিয়ে একসঙ্গে পরিবর্তন করলে একটি সফল হবে; অন্যটিকে সর্বশেষ তথ্য আনতে হবে।

চালু চাহিদা সাময়িক বন্ধ, পুনরায় চালু, পূরণ হয়েছে হিসেবে চিহ্নিত বা স্থায়ীভাবে মুছে ফেলা যায়। পূরণ হওয়া চাহিদাও প্রয়োজনে আবার চালু করা যায়। অবস্থা বদলানো বা মুছে ফেলার সুযোগ দুইবার সম্পাদনার পরেও থাকে; এগুলো সম্পাদনার সংখ্যা ব্যবহার বা পুনরায় শুরু করে না। পূরণ বা মুছে ফেলার আগে নিশ্চিত করার সংলাপ আসে।

এটি ক্রেতার ব্যক্তিগত তালিকা; অন্য ক্রেতা, কৃষক বা অ্যাডমিন এই ব্যক্তিগত API দিয়ে দেখতে বা বদলাতে পারবেন না। অপেক্ষমাণ/প্রত্যাখ্যাত ক্রেতার প্রবেশ বন্ধ থাকে। অনুমোদন বদলে গেলে বর্তমান সেশনেও পরের অনুরোধে সেটি কার্যকর হয়। প্রতিটি পরিবর্তনের transaction-এ অনুমোদন পুনরায় যাচাই এবং সম্পাদনার সংখ্যা/সংস্করণ একসঙ্গে সংরক্ষণ করা হয়। সর্বোচ্চ ১২টি চাহিদা প্রতি পাতায় দেখা যায়; অবস্থা দিয়ে বাছাই করা যায়।

প্রথমবার চাহিদা চালু করতে `npm run db:migrate` দিয়ে `purchase_requirements` টেবিল প্রস্তুত করুন। আগের অ্যাকাউন্ট বা বিজ্ঞাপনের তথ্য বদলায় না।

## কৃষকদের সম্মিলিত সরবরাহ

বিজ্ঞাপন ও চাহিদায় একই ফসলের তালিকা ব্যবহৃত হয়। ক্রেতা জাত বেছে নিলে কৃষকের বিজ্ঞাপনেও সেই জাত থাকতে হবে। জাত খালি রাখলে একই ফসলের সব জাত ও অনির্দিষ্ট জাত গ্রহণযোগ্য। মাইগ্রেশন পরিচিত পুরোনো নামগুলোকে তালিকার সঙ্গে যুক্ত করে। ফসল, জাত ও পরিচিত বানানের তালিকা `shared/crop-catalog.js` ফাইলে আছে। অপরিচিত নাম মালিকের তালিকায় চিহ্নিত হয় এবং শনাক্ত করার আগ পর্যন্ত শুধু একই পুরোনো নামের সঙ্গে মিলতে পারে।

**ক্রয় চাহিদা → মিলে যাওয়া ফসল দেখুন** খুলুন। একই ফসল ও এককের চালু, মজুত থাকা এবং যাচাইকৃত কৃষকের বিজ্ঞাপনগুলো থেকে সর্বোচ্চ পাঁচটি সমন্বয় দেখায়। একটি সমন্বয়ে এক বা একাধিক কৃষকের ফসল থাকতে পারে। একই কৃষকের একাধিক বিজ্ঞাপন থাকলে তাঁর সংখ্যা একবারই গণনা হয়। একজন কৃষক পুরো চাহিদা মেটাতে পারলে সেই বিকল্পগুলো আগে দেখানো হয়। তাঁর একাধিক বিজ্ঞাপন বেছে নিলে বড় মজুত থেকে শুরু করে যতটুকু প্রয়োজন ততটুকু নেওয়া হয়। একাধিক কৃষকের সমন্বয়ে নির্বাচিত বিজ্ঞাপনগুলোর পুরো মজুত যোগ হয়। একই বিজ্ঞাপন একাধিক বিকল্প সমন্বয়ে থাকতে পারে; এগুলো পরস্পরের বিকল্প।

প্রকল্পের মালিকের অনুমোদিত নিয়ম: আগে ঠিক সমান পরিমাণ, তারপর চাহিদার সর্বোচ্চ **২০% অতিরিক্ত**, শেষে চাহিদার অন্তত **৮০%** মেটায় এমন আংশিক সরবরাহ। এই সর্বনিম্ন পরিমাণটি সমন্বয়ের মোট সরবরাহের ওপর প্রযোজ্য। একই শ্রেণিতে ক্রমানুসারে **আগে সরবরাহ → আগে ফসল কাটা → কম মোট দাম → কম কৃষক → কাছাকাছি অবস্থান** দিয়ে তুলনা হয়। সবগুলো সমান হলে বিজ্ঞাপনের স্থায়ী ID দিয়ে একই ক্রম রাখা হয়। মোট পরিমাণ ৩ ঘর দশমিকের পূর্ণসংখ্যা স্কেলে গণনা হয়, ফলে ভাসমান দশমিকের কারণে ২০% সীমা অতিক্রম করে না। প্রতিটি বিজ্ঞাপনের পরিমাণ × একক দাম নিকটতম পয়সায় round করে উপমোট হয়; উপমোটগুলোর যোগই মোট পণ্যমূল্য। পরিবহন খরচ এতে নেই।

সমন্বয়ের সরবরাহ ও ফসল কাটার তারিখ হলো সদস্যদের সংশ্লিষ্ট সর্বশেষ তারিখ—সব ফসল তখন পাওয়া যাবে। অনুমোদিত আনুমানিক নৈকট্য জেলা–উপজেলার ভিত্তিতে: ভিন্ন কৃষকদের বিজ্ঞাপনের প্রতিটি জোড়ায় একই উপজেলা ও জেলা হলে ০, একই জেলার অন্য উপজেলা হলে ১, ভিন্ন জেলা হলে ২; জোড়াগুলোর গড় কম হলে আগে আসে। একই নামে উপজেলা ভিন্ন জেলায় হলে সেটি একই উপজেলা ধরা হয় না। এটি GPS, কিলোমিটার বা সড়কপথের দূরত্ব নয়; অবস্থান দিয়ে কোনো যোগ্য কৃষক বাদ দেওয়া হয় না।

ক্রেতা দাম, সরবরাহের তারিখ, ফসল কাটার তারিখ, কৃষকের সংখ্যা অথবা আনুমানিক নৈকট্য—একটি বিষয় আগে রেখে সাজাতে পারবেন। পূরণ হওয়ার শ্রেণির অগ্রাধিকার বজায় থাকে; এরপর নির্বাচিত বিষয়, তারপর বাকি ডিফল্ট বিষয়গুলো দিয়ে তুলনা করে আবার সেরা পাঁচটি নেওয়া হয়। প্রতিটি ফলাফলে মোট পরিমাণ, পণ্যমূল্য, অতিরিক্ত/ঘাটতি, কৃষকের সংখ্যা এবং প্রত্যেকের পরিমাণ, দাম, উপমোট, তারিখ, নাম, ফোন ও খামারের ঠিকানা দেখা যায়। বিস্তারিত থেকে ফিরলে সাজানোর ধরন থাকে।

চাহিদার মালিক অনুমোদিত ক্রেতা এই ফলাফল দেখতে পারেন। দেখা ও হালনাগাদ করলে চাহিদার সংস্করণ বা সম্পাদনার সংখ্যা বদলায় না; বন্ধ বা পূরণ হওয়া চাহিদার বর্তমান মিলও দেখা যায়। শুধু ফলাফল দেখলে মজুত সংরক্ষণ হয় না। **এই সমন্বয় থেকে অর্ডার দিন** খুলে নিশ্চিত করলে নির্বাচিত সব বিজ্ঞাপনের মজুত একসঙ্গে সংরক্ষিত হবে।

অনুসন্ধানে কোনো নির্দিষ্ট সংখ্যক কৃষক বা প্রাথমিক বিজ্ঞাপনের নমুনা নিয়ে বাকিগুলো বাদ দেওয়া হয় না। পরিমাণ ও র‍্যাঙ্কিংয়ের নিরাপদ bounds দিয়ে অসম্ভব/অপ্রয়োজনীয় শাখা বাদ যায়। অনেক সম্ভাবনা থাকলে সম্পূর্ণ সেরা পাঁচটি প্রমাণ করতে সময় লাগতে পারে: প্রায় ৩ সেকেন্ডের গণনা শেষে কাজ অসম্পূর্ণ থাকলে API `503` ও বাংলা বার্তা দেয়, আংশিক ফলকে সেরা হিসেবে দেখায় না। এ অবস্থায় বড় তথ্যের জন্য ভবিষ্যতে পটভূমিতে দীর্ঘ অনুসন্ধান যুক্ত করা যাবে।

## অর্ডার, সংরক্ষিত মজুত ও কৃষকের উত্তর

মূল ফোল্ডার থেকে `npm run db:migrate` চালান। এই ধাপ `crop_listings.reserved_quantity`, `orders`, `order_portions`, `order_items` ও `notifications` প্রস্তুত করে। পুরোনো বিজ্ঞাপনের উন্মুক্ত মজুত অপরিবর্তিত থাকে; সংরক্ষিত মজুত শুরুতে শূন্য।

নিজের চালু চাহিদার সম্মিলিত সরবরাহ থেকে **অর্ডার দিন** খুলুন। সর্বশেষ পরিমাণ, দাম, কৃষকভিত্তিক উপমোট, মোট পণ্যমূল্য, ডেলিভারির ঠিকানা ও নির্দেশনা দেখাবে। একজন কৃষক পুরো চাহিদা মেটালে অর্ডারে প্রয়োজনীয় পরিমাণ নেওয়া হয়। একাধিক কৃষকের সমন্বয়ে প্রতিটি নির্বাচিত বিজ্ঞাপনের পুরো উন্মুক্ত মজুত নেওয়া হয়। আংশিক বা অতিরিক্ত পরিমাণের অর্ডার হলে নিশ্চিত করার আগে স্পষ্ট বার্তা থাকে। বন্ধ/পূরণ হওয়া চাহিদা দেখা যায়, তবে নতুন অর্ডার দিতে চালু করতে হয়। দুইবার সম্পাদনার সুযোগ শেষ হলেও অর্ডার দেওয়া যায়।

নিশ্চিত করার সময় সার্ভার অনুমোদন, মালিকানা, ফসল, জাত ও একক, চালু মজুত, পরিমাণ এবং চাহিদা ও বিজ্ঞাপনের সংস্করণ আবার পরীক্ষা করে। দেখার পরে দাম বা মজুত বদলালে `409` দেয়; সর্বশেষ তথ্য আবার খুলে সম্মতি দিতে হয়। ক্রেতার পাঠানো দাম, মোট মূল্য, মালিকানা বা status গ্রহণ করা হয় না। সব নির্বাচিত মজুত, অর্ডার, কৃষকের অংশ ও নোটিফিকেশন একই transaction-এ সংরক্ষিত হয়। দুই ক্রেতা একই মজুত কিনতে চাইলে row lock দিয়ে অতিরিক্ত সংরক্ষণ রোধ হয়। নিশ্চিত করার অনুরোধে `requestId` একই রেখে পুনরায় পাঠালে একই অর্ডার ফিরে আসে; দ্বিতীয় অর্ডার বা নোটিফিকেশন হয় না।

`quantity` এখন নতুন অর্ডারের জন্য **উন্মুক্ত মজুত**, `reservedQuantity` অপেক্ষমাণ বা গৃহীত অর্ডারের জন্য আটকে থাকা মজুত। বাজার ও সরবরাহের সমন্বয় শুধু উন্মুক্ত পরিমাণ দেখায়। কৃষকের নিজের বিজ্ঞাপনে দুটি পরিমাণ আলাদা বোঝানো আছে। সব মজুত সংরক্ষিত হলে বাজার থেকে বিজ্ঞাপন সাময়িক অদৃশ্য হয়; নিজের তালিকা ও অর্ডারে থাকে।

প্রতিটি আলাদা কৃষকের একটি অংশ থাকে; একই কৃষকের একাধিক বিজ্ঞাপন হলে সেই অংশে একসঙ্গে থাকে। কৃষক শুধু নিজের অংশ এবং সংশ্লিষ্ট ক্রেতার ডেলিভারির নাম, ফোন, ব্যবসার নাম, ঠিকানা ও নির্দেশনা দেখেন। অন্য কৃষকের অংশ, যোগাযোগ ও পণ্যমূল্য পাঠানো হয় না। অনুমোদিত মালিক ক্রেতা পুরো অর্ডার দেখেন; অন্য ক্রেতা বা অ্যাডমিন এই ব্যক্তিগত API ব্যবহার করতে পারেন না। অনুমোদন প্রত্যাহার হলে ক্রেতার অর্ডার পরিচালনাও বন্ধ হয়।

**কৃষকের উত্তর দেওয়ার সময়সীমা নেই।** অপেক্ষমাণ অংশ নিজে থেকে বাতিল/মেয়াদোত্তীর্ণ হয় না। নিজের অংশ গ্রহণ করলে সংশ্লিষ্ট মজুত সংরক্ষিত থাকে; প্রত্যাখ্যান করলে ওই অংশের সব বিজ্ঞাপনের সংরক্ষণ একবারই ছেড়ে দেওয়া হয়। বিজ্ঞাপন কৃষক আগে বন্ধ রাখলে মজুত ফেরত এলেও সেটি বন্ধ থাকে। একই উত্তর আবার পাঠালে কোনো বাড়তি পরিবর্তন হয় না; প্রথম উত্তরের পরে বিপরীত সিদ্ধান্ত দেওয়া যায় না। আলাদা কৃষক একসঙ্গে উত্তর দিলেও ক্রেতার গৃহীত, অপেক্ষমাণ ও প্রত্যাখ্যাত পরিমাণের হিসাব অক্ষুণ্ণ থাকে।

সংরক্ষিত মজুত থাকা অবস্থায় বিজ্ঞাপন মোছা, বিক্রি শেষ করা বা ফসল, জাত ও একক বদলানো যাবে না। উন্মুক্ত পরিমাণ, ভবিষ্যতের দাম/তারিখ, ঠিকানা, বিবরণ ও ছবি সম্পাদনা করা যায়; সংরক্ষিতসহ মোট পরিমাণ কলামের সীমার মধ্যে থাকতে হবে। সম্পূর্ণ সংরক্ষিত বিজ্ঞাপনের উন্মুক্ত মজুত শূন্য রেখেও তথ্য সম্পাদনা করা যায়। অর্ডারে তখনকার পরিমাণ, দাম, নাম, ফোন ও ঠিকানার snapshot থাকে; পরের বিজ্ঞাপন পরিবর্তন বা চাহিদা মুছে ফেললে পুরোনো অর্ডার বদলায় না। প্রত্যাখ্যানের পরে মজুত আর সংরক্ষিত না থাকলে বিজ্ঞাপন মোছা যায়, অর্ডারের ইতিহাস থাকে। NID, ইমেইল, পাসওয়ার্ড বা সেশন অর্ডারের snapshot-এ রাখা হয় না।

ঐচ্ছিক `ORDER_QUOTE_SECRET` মূল `.env.example`-এ আছে। স্থানীয় development-এ খালি রাখা যায়; তখন backend পুনরায় চালু করলে পুরোনো নিশ্চিতকরণের তথ্য আবার খুলতে হয়। একাধিক backend instance বা স্থায়ী পরিবেশে একই দীর্ঘ random secret ব্যবহার করুন। এটি অর্ডারের আগে দেখানো তথ্যের স্বাক্ষরের জন্য; কৃষকের উত্তর দেওয়ার সময়সীমা তৈরি করে না। নিশ্চিত হওয়া অর্ডার ও সংরক্ষণ ডেটাবেসে থাকে এবং সার্ভার পুনরায় চালুর পরেও থাকে।

**আমার অর্ডার → অর্ডারের বিস্তারিত** থেকে কৃষক নিজের গৃহীত অংশের অগ্রগতি জানাতে পারেন। ধাপগুলো হলো প্রস্তুতি চলছে → সংগ্রহের জন্য প্রস্তুত → সংগ্রহ করা হয়েছে → এই অংশের কাজ সম্পন্ন। প্রতিটি পরিবর্তনে ক্রেতা অ্যাপে খবর পান। অংশ সম্পন্ন হলে তার মজুত সংরক্ষণ শেষ হয়।

## প্রত্যাখ্যাত সরবরাহের বিকল্প কৃষক

মূল ফোল্ডার থেকে `npm run db:migrate` চালান। `20261123-008-order-replacements.js` অর্ডারের সংস্করণ, বিকল্প সংযোজনের ইতিহাসের `order_replacements` টেবিল ও কৃষকের অংশের সঙ্গে তার সম্পর্ক যোগ করে। নতুন পরিবেশের সেটিংস প্রয়োজন নেই।

অনুমোদিত মালিক ক্রেতা **আমার অর্ডার → অর্ডার বিস্তারিত → বিকল্প সরবরাহ বেছে নিন** খুলবেন। প্রত্যাখ্যানের কারণে ঘাটতি থাকলে অর্ডার খোলার সময় সর্বোচ্চ পাঁচটি পরামর্শ খোঁজা হয়। আগে ওই অর্ডারে থাকা সব কৃষককে বাদ দিয়ে একই ফসল ও এককের চালু, উন্মুক্ত মজুত থাকা যাচাইকৃত কৃষক নেওয়া হয়। কৃষকের নাম, ফোন ও খামারের ঠিকানা দেখা যায়। মূল চাহিদা পরে বদলালেও বা মুছলেও অর্ডারের সংরক্ষিত তথ্য দিয়ে বিকল্প খোঁজা হয়।

বাকি পরিমাণ হলো **প্রথম অর্ডারের মোট বরাদ্দ − বর্তমানে গৃহীত ও অপেক্ষমাণ পরিমাণ**। যেমন, চাহিদা ১,০০০ কেজি হলেও প্রথম অর্ডার ৮০০ কেজির হলে তার ৩০০ কেজি প্রত্যাখ্যাত হওয়ার পরে বিকল্প খোঁজা হবে ৩০০ কেজির জন্য। মূল চাহিদার আগে থেকেই অপূর্ণ ২০০ কেজি এতে যোগ হয় না।

একটি বিজ্ঞাপন বাছলে প্রয়োজনের বেশি মজুত থেকে শুধু বাকি পরিমাণ নেওয়া হয়; কম থাকলে আংশিক নেওয়া যায়। একাধিক বিজ্ঞাপন বাছলে প্রত্যেকটির পুরো উন্মুক্ত মজুত যোগ হয় এবং মোট পরিমাণ ঘাটতির সর্বোচ্চ ২০% অতিরিক্ত হতে পারে। স্বয়ংক্রিয় পরামর্শে একক বিজ্ঞাপন ও অন্তত দুই কৃষকের সমন্বয় তুলনা হয়; কৃষকের সংখ্যার নির্দিষ্ট সীমা নেই। আগের মতোই সম্পূর্ণ পূরণ, অতিরিক্ত, আংশিক—এরপর তারিখ, মূল্য, কৃষকের সংখ্যা ও জেলা–উপজেলার আনুমানিক নৈকট্যের অগ্রাধিকার থাকে। সাজানোর বিষয় বদলানো যায়। অনুসন্ধানের গণনা প্রায় ৩ সেকেন্ডে শেষ না হলে স্পষ্ট ব্যর্থতা দেখায়; নিজে বিজ্ঞাপন বাছার সুবিধা আলাদা থাকে।

নিজে বাছার তালিকায় জেলা–উপজেলা, দাম, পরিমাণ বা তারিখ দিয়ে খোঁজা যায়। প্রতি পাতায় ১২টি বিজ্ঞাপন থাকে; পাতা বা ফিল্টার বদলালেও নির্বাচন থাকে। একই নতুন কৃষকের একাধিক বিজ্ঞাপনও নেওয়া যায়। **শুধু দেখা বা বাছলে মজুত আটকে যায় না।** সর্বশেষ পরিমাণ, মোট মূল্য ও ডেলিভারির তথ্য দেখে ক্রেতা নিশ্চিত করলে একই অর্ডারে নতুন অংশ, সংরক্ষিত মজুত ও নোটিফিকেশন একসঙ্গে তৈরি হয়। কৃষক উত্তর দেওয়ার জন্য আগের মতোই সীমাহীন সময় পান।

নিশ্চিত করার আগে অর্ডারের সংস্করণ, ঘাটতি, বিজ্ঞাপনের সংস্করণ, দাম ও মজুত আবার পরীক্ষা হয়। অন্য ট্যাবে বিকল্প যোগ হলে বা কোনো কৃষক উত্তর দিলে পুরোনো নিশ্চিতকরণে `409` আসে এবং নতুন তথ্য দেখতে হয়। একই অনুরোধ পুনরায় পাঠালে দ্বিতীয় সংযোজন বা নোটিফিকেশন হয় না। অন্য ক্রেতার অর্ডারের সঙ্গে একই মজুতের প্রতিযোগিতাতেও অতিরিক্ত সংরক্ষণ হয় না।

প্রত্যাখ্যানের পুরোনো অংশ ইতিহাসে থাকে। বর্তমান পরিমাণ ও পণ্যমূল্যে শুধু গৃহীত ও অপেক্ষমাণ অংশ গণনা হয়; প্রথম অর্ডারের হিসাব আলাদা থাকে। বিকল্প কৃষকও প্রত্যাখ্যান করলে তাঁর মজুত একবারই ফেরে এবং ঘাটতি আবার খোলে। জমা হওয়া প্রত্যাখ্যানের ইতিহাস বর্তমান ঘাটতি হিসেবে দ্বিগুণ গণনা হয় না। ঘাটতি পূরণ হয়ে সব বর্তমান অংশ গৃহীত হলে পুরোনো প্রত্যাখ্যান রেখেই অর্ডারের বর্তমান অবস্থা গৃহীত হয়।

## অ্যাপের নোটিফিকেশন

নেভিগেশনের ঘণ্টা থেকে **নোটিফিকেশন** খুলুন। নতুন অর্ডারে সংশ্লিষ্ট প্রতিটি কৃষক ও ক্রেতা খবর পান; গ্রহণ/প্রত্যাখ্যানে ক্রেতা গৃহীত, অপেক্ষমাণ ও এখনো প্রয়োজনীয় পরিমাণের খবর পান। আগের খবর, পড়া বাকি সংখ্যা, পৃথক/সব পড়া চিহ্নিত করা ও সংশ্লিষ্ট অর্ডার খোলা যায়। নোটিফিকেশন কেবল প্রাপক দেখতে বা পড়া চিহ্নিত করতে পারেন। প্রতি পাতায় ২০টি; অর্ডারে প্রতি পাতায় ১২টি। ঘণ্টার সংখ্যা পাতা বদলানো, কাজ সম্পন্ন করা, উইন্ডোতে ফিরে আসা এবং দৃশ্যমান অবস্থায় প্রায় ৩০ সেকেন্ড পরপর হালনাগাদ হয়।

এখন শুধু অ্যাপের ভেতরের নোটিফিকেশন চালু। Email বা browser push পাঠানো হয় না; সেসব চ্যানেল এবং তাদের নির্দিষ্ট event পরবর্তী ধাপ।

## কৃষকের নিবন্ধন ও লগইন পরীক্ষা

১. মূল ফোল্ডারের `.env`-এ MySQL সংযোগ ঠিক করুন এবং `npm run db:migrate` চালান। সার্ভার ও ফ্রন্টএন্ড আলাদা টার্মিনালে চালু রাখুন।

২. **http://localhost:5174/register** খুলে নাম, মোবাইল নম্বর, পাসওয়ার্ড ও তার নিশ্চিতকরণ, NID নম্বর এবং খামারের অবস্থান ও ঠিকানা লিখুন। বাংলা ও ইংরেজি দুই ধরনের সংখ্যা গ্রহণ করা হয়। `+880`-সহ নম্বরও স্বাভাবিক স্থানীয় নম্বরে রূপান্তরিত হয়। NID নম্বরের দৈর্ঘ্য পরীক্ষা করা হয়; সরকারি NID যাচাইকরণ সেবা যুক্ত করা হয়নি।

৩. চাইলে “আরও কিছু তথ্য” খুলে ইমেইল, খামারের নাম ও একটি প্রোফাইল ছবি যোগ করুন। প্রোফাইলের ছবি ঐচ্ছিক; NID-এর ছবি দেবেন না। ছবির সীমা ২ মেগাবাইট। সার্ভার প্রকৃত ছবি যাচাই করে সর্বোচ্চ ৩২০×৩২০ পিক্সেলের WebP হিসেবে সংরক্ষণ করে।

৪. “ফোন যাচাই করুন” চাপুন। **ব্যাকএন্ড চলা টার্মিনালে** `[ফিল্ডব্রিজ OTP]` লাইনের ৬ সংখ্যার কোডটি দেখুন। সেটি দিয়ে অ্যাকাউন্ট তৈরি করুন। এখন SMS পাঠানো হয় না; OTP কখনো HTTP উত্তরে দেওয়া হয় না।

৫. সফল হলে `/account` খুলবে। লগআউট করে ফোন নম্বর বা নিবন্ধনের সময় দেওয়া ইমেইল ও পাসওয়ার্ড দিয়ে আবার প্রবেশ করতে পারবেন।

OTP-এর মেয়াদ ৫ মিনিট, নতুন কোড নেওয়ার বিরতি ৬০ সেকেন্ড এবং সর্বোচ্চ ভুল চেষ্টা ৫ বার। কোড একবারই ব্যবহার করা যায়। একই ফোন, ইমেইল বা NID দিয়ে দ্বিতীয় কৃষক অ্যাকাউন্ট তৈরি হবে না। নিবন্ধনের পর ফোন ও NID পরিবর্তনের কোনো API দেওয়া হয়নি। অ্যাকাউন্টের উত্তরে পুরো NID পাঠানো হয় না; শেষ চারটি সংখ্যা দেখানো হয়।

`OTP_MODE=console` development-এর জন্য। `NODE_ENV=production` হলে console OTP সবসময় বন্ধ থাকবে; production-এ ফোন যাচাই চালুর আগে বাস্তব SMS সেবা যুক্ত করতে হবে। `OTP_SECRET` development-এ ঐচ্ছিক। এটি না দিলে সার্ভার চালুর সময় অস্থায়ী secret তৈরি হয়; সার্ভার পুনরায় চালু হলে আগের অপেক্ষমাণ OTP বাতিল হয়ে যায়। স্থায়ী দীর্ঘ random `OTP_SECRET` দিলে অপেক্ষমাণ কোড সার্ভার পুনরায় চালুর পরও তার নির্ধারিত মেয়াদ পর্যন্ত কাজ করবে।

সেশন MySQL-এ থাকে এবং `HttpOnly`, `SameSite=Lax` cookie ব্যবহার করে; production-এ cookie-তে `Secure`-ও থাকে। পাসওয়ার্ড scrypt দিয়ে hash করা হয়। সেশনের আসল token বা পাসওয়ার্ড ব্রাউজারের localStorage-এ রাখা হয় না। লগআউট করলে সংশ্লিষ্ট সেশন বাতিল হয়।

## পরিবেশের সেটিংস

মূল `.env`-এ `PORT`, `HOST`, `CLIENT_ORIGIN` এবং `DB_*` মানগুলো থাকবে। `CLIENT_ORIGIN`-এ ব্রাউজারে ব্যবহৃত ফ্রন্টএন্ডের সঠিক origin দিন, যেমন `http://localhost:5174`।

`client/.env`-এ `VITE_API_BASE_URL=/api` থাকলে Vite `/api` অনুরোধগুলো `API_PROXY_TARGET` ঠিকানায় পাঠাবে। `DEV_PORT` দিয়ে ফ্রন্টএন্ডের পোর্ট বদলানো যাবে। ব্যাকএন্ডের পোর্ট বদলালে `API_PROXY_TARGET`-ও বদলান; ফ্রন্টএন্ডের পোর্ট বদলালে `CLIENT_ORIGIN` বদলান।

ডেটাবেসের তথ্য শুধুমাত্র মূল `.env`-এ রাখুন। `VITE_` দিয়ে শুরু হওয়া সেটিংস ব্রাউজারে প্রকাশিত হয়।

পোর্ট আগে থেকেই ব্যবহৃত হলে অন্য প্রোগ্রাম বন্ধ না করে `.env`-এ আলাদা পোর্ট দিন। উদাহরণস্বরূপ মূল `.env`-এ `PORT=5055` ও `CLIENT_ORIGIN=http://localhost:5175` এবং `client/.env`-এ `DEV_PORT=5175` ও `API_PROXY_TARGET=http://127.0.0.1:5055` দিন। এরপর উভয় সার্ভার পুনরায় চালু করুন।

## MySQL সংযোগ

নিজের MySQL সার্ভারে `utf8mb4`-সমর্থিত একটি ডেটাবেস ও তার উপযুক্ত ব্যবহারকারী তৈরি করুন। মূল `.env`-এ তার সংযোগ তথ্য দিয়ে চালান:

```bash
npm run db:check
```

এই কমান্ড শুধু সংযোগ পরীক্ষা করে। অ্যাকাউন্টের টেবিল প্রস্তুত করতে মূল ফোল্ডারে চালান:

```bash
npm run db:migrate
```

মাইগ্রেশন `users`, `farmer_profiles`, `buyer_profiles`, `phone_verifications`, `auth_sessions`, `crop_listings`, `purchase_requirements`, `orders`, `order_portions`, `order_items`, `order_replacements`, `notifications` এবং মাইগ্রেশন ইতিহাসের `SequelizeMeta` টেবিল প্রস্তুত করে। একই মাইগ্রেশন বারবার চালালে আগের মাইগ্রেশন আবার চালানো হয় না। অ্যাপ চালুর সময় স্বয়ংক্রিয় `sync`, `alter` বা টেবিল মুছে তৈরি করার কোনো ব্যবস্থা নেই।

| `GET /api/marketplace/listings` | সক্রিয় মজুতের বাজার; অনুমোদনভিত্তিক দাম ও ফিল্টার |
| `GET /api/marketplace/listings/:id` | বিজ্ঞাপনের বিস্তারিত; অনুমোদিত ক্রেতা/অ্যাডমিনের জন্য কৃষকের নির্ধারিত যোগাযোগের তথ্য |
| `GET /api/marketplace/listings/:id/photos/:filename` | সক্রিয় মজুতের বিজ্ঞাপনের ছবি; বন্ধ হলে 404 |
| অন্য ঠিকানা | 404 এবং বাংলা JSON বার্তা |

প্রথম স্বাস্থ্য পরীক্ষায় `not_configured` মানে `.env`-এ ডেটাবেসের তথ্য নেই; `not_checked` মানে তথ্য আছে, সংযোগ এখনো পরীক্ষা করা হয়নি।

অ্যাকাউন্টের POST/PATCH অনুরোধে `Origin` অবশ্যই `CLIENT_ORIGIN`-এর সঙ্গে মিলতে হবে। তাই ব্রাউজারে ফ্রন্টএন্ডের সঠিক ঠিকানা ব্যবহার করুন। development-এ `/api` proxy ব্যবহার করলে cookie একই origin-এ থাকে।

## যাচাই ও বিল্ড

মূল ফোল্ডারে ব্যাকএন্ড পরীক্ষা:

```bash
npm test
```

আসল MySQL-এ কৃষক ও ক্রেতার নিবন্ধন, OTP, সেশন, ছবির আপলোড, অ্যাডমিন তৈরির কমান্ড, ভূমিকার অনুমতি, আবেদন পর্যালোচনা, ফসলের বিজ্ঞাপন পরিচালনা এবং বাজারের ফিল্টার ও তথ্য গোপন রাখার পরীক্ষা:

```bash
npm run test:integration
```

এই পরীক্ষা একই ডেটাবেসে প্রতিটি suite-এর জন্য স্বতন্ত্র `fb_test_..._` নামের টেবিল ব্যবহার করে এবং শেষে সেগুলো মুছে দেয়। অ্যাকাউন্ট/বাজার এবং ক্রয় চাহিদার পরীক্ষা আলাদা তথ্য ব্যবহার করে। চাহিদার পরীক্ষায় অনুমোদন, মালিকানা, একই সময়ে দুই ট্যাবের পরিবর্তন, দুইবারের সীমা ও অবস্থা পরিবর্তনের সময় সংখ্যা অপরিবর্তিত থাকা যাচাই হয়। ফসল মেলানোর পরীক্ষায় সঠিক নাম/একক/দশমিক মজুত, বন্ধ বিজ্ঞাপন বাদ দেওয়া, সাজানো, পাতায় ভাগ, অনুমোদন প্রত্যাহার ও ব্যক্তিগত তথ্য সুরক্ষা যাচাই হয়। অ্যাপের আসল টেবিলে পরীক্ষার অ্যাকাউন্ট লেখা হয় না। আলাদা ডেটাবেস তৈরির অনুমতি প্রয়োজন হয় না।

সম্মিলিত সরবরাহের পৃথক suite-এ তিন ধরনের পূরণ, ২০% সীমা, প্রত্যেক সদস্যের অনুমোদিত তথ্য, সাজানো, মজুত বদল, অপরিবর্তিত সম্পাদনা সংখ্যা ও পয়সার rounding পরীক্ষা হয়। unit পরীক্ষায় ছোট নমুনার সব সম্ভাব্য subset স্বাধীনভাবে গণনা করে প্রতিটি সাজানোর সেরা পাঁচটির সঙ্গে মেলানো হয়; ৪০ কৃষকের সমন্বয়, একই কৃষকের একাধিক বিজ্ঞাপন, আনুমানিক নৈকট্য এবং সময়সীমায় স্পষ্ট ব্যর্থতাও যাচাই হয়।

অর্ডারের suite-এ স্বাক্ষরিত নিশ্চিতকরণ, পুরোনো দাম/মজুত প্রত্যাখ্যান, একই অনুরোধের পুনরাবৃত্তি, দুই ক্রেতার একই মজুতের প্রতিযোগিতা, এক কৃষকের একাধিক বিজ্ঞাপন, আলাদা উত্তরের গোপনীয়তা, একসঙ্গে গ্রহণ/প্রত্যাখ্যান, মজুত একবারই ফেরত আসা, সময়সীমা না থাকা, পুরোনো snapshot ও নোটিফিকেশনের মালিকানা যাচাই হয়।

বিকল্পের পৃথক suite-এ অনুমতি, আগে থাকা কৃষক বাদ দেওয়া, পরামর্শে মজুত অপরিবর্তিত থাকা, ফিল্টার ও পাতা, আংশিক/২০% সীমা, একই অনুরোধের পুনরাবৃত্তি, পুরোনো নিশ্চিতকরণ, দুই ট্যাব ও অন্য ক্রেতার মজুতের প্রতিযোগিতা এবং বিকল্পও প্রত্যাখ্যাত হওয়ার পরে সঠিক ঘাটতি যাচাই হয়। unit পরীক্ষায় পুরোনো প্রত্যাখ্যান রেখেও বর্তমান পরিমাণ, খরচ ও অবস্থা পরীক্ষা হয়।

ফ্রন্টএন্ডের বিল্ড:

```bash
cd client
npm run build
npm run preview
```

বিল্ড `client/dist`-এ তৈরি হবে। প্রোডাকশন হোস্টিং যুক্ত করার সময়ে ফ্রন্টএন্ডের সব রুটকে `index.html`-এ পাঠানোর SPA fallback এবং `/api`-র জন্য Express proxy আলাদাভাবে কনফিগার করতে হবে। Vite-এর development proxy প্রোডাকশন বিল্ডে থাকে না।

## নকশার সিদ্ধান্ত

`DESIGN.md`-এর ওপরের টোকেন তালিকাকে এই ধাপের রঙের মূল উৎস ধরা হয়েছে। নিচের বর্ণনামূলক অংশে ভিন্ন রঙ রয়েছে; সেটিকে মিশিয়ে দ্বিতীয় প্যালেট করা হয়নি। সব রঙ `client/src/tokens.css`-এ এবং responsive নকশা `client/src/styles.css`-এ আছে।

শিরোনামে Atma এবং বাকি লেখায় Anek Bangla ব্যবহার হয়েছে। ফন্টগুলো npm প্যাকেজ থেকে নিজের বিল্ডে যুক্ত হয়; Google Fonts-এর আলাদা অনুরোধ প্রয়োজন হয় না। সব ব্যবহারকারীমুখী লেখা বাংলায়।
